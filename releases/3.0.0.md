# PlexonShops 3.0.0

Stable GitHub repository closure of the accepted PlexonShops Phase 2 / Phase 3 player-shop directory line and final RC2 UX, plus one transaction-safety correction discovered during the final source audit.

## Player-shop product boundary

PlexonShops remains the player-owned shop discovery and directory product. It owns browse/search/filter, categories, featured shops, favorites, recent shops, profiles, ratings, showcased items, owner listing management, safe shop visits, and teleport fee/refund orchestration.

DynamicShop remains PlexonCraft's server-owned item buy/sell `/shop` authority. PlexonShops does not add item pricing, stock, purchase quantities, payouts, or another server-commerce engine.

## Final stability fix

A paid shop visit now keeps the in-flight Paper `teleportAsync` result authoritative across player logout.

Previously, `PlayerQuitEvent` removed the in-flight attempt and refunded its Vault fee immediately even though the already-started asynchronous teleport itself was not cancelled. If that teleport later completed successfully, its callback was ignored as stale, creating a possible refunded successful teleport.

Stable 3.0 changes the boundary:

- logout cancels only a still-pending warmup;
- once `teleportAsync` starts, logout does not refund or revoke the attempt;
- failed/exceptional async completion owns the refund;
- successful completion owns visit publication/cooldown settlement;
- player-facing completion effects/messages are skipped when the player is no longer online;
- duplicate/stale callbacks remain identity-guarded.

## Stability architecture retained

- one accepted warmup/in-flight visit per player;
- destination/shop availability revalidation immediately before charge;
- Vault/Theosis economy remains authoritative for teleport fees;
- failed teleports refund the exact charged amount;
- one shared bossbar warmup coordinator rather than one repeating task per teleport;
- generation-guarded asynchronous discovery loads;
- bounded SQLite worker and WAL persistence;
- serialized per-shop mutation chains;
- coalesced visit persistence with bounded diagnostics;
- cached/paginated directory views and stale GUI revision rejection;
- schema 3 forward migration with backup and fail-closed newer-schema handling.
